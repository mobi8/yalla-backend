# RAID Bot Operations — local implementation and deployment notes

No deployment or data modification is performed by this document. `bots.json` is a private `game-config/<environment>/v1/bots.json` object in the existing `GAME_CONFIG_BUCKET`. It replaces the earlier unshipped `balance.json` bot setting. Existing bot IDs and profiles are retained; four new templates reuse existing avatar artwork. Shield regeneration is lazy; existing bot shield counts are never reset. Missing timestamps start at first observation, and a full shield clears its timer. The new period applies to all uncredited elapsed time.

`incomingRaid.enabled` defaults to false, including on cold S3 failure. A valid config is cached for 60 seconds; failures retain the last valid config in that execution environment. `allowedPlayerIds` is an allowlist when non-empty; an empty list permits all players **if enabled is true**. It is not a security boundary for the API; only the internal worker can settle attacks. `shield.maximum` and `shieldConsumption` are constrained to 3 and 1. Daily mean ranges from 1 to 3, and maximum must be at most 3 and at least the mean.

## State and execution

New accounts receive `INCOMING#SCHEDULE` in the same transaction as player creation. It contains `duePartition`, `dueAt`, `sequence`, and the last UTC execution day/count, with a version. GSI `IncomingDue` has 16 shards and projects `playerId`. Every five minutes EventBridge invokes a Lambda that queries due schedules, strongly reads each schedule and collection, and transactionally writes an updated schedule, COLLECTION and an immutable `INCOMING#RECEIPT#<sequence>`. Version conditions and receipt absence protect against retries and concurrent collection grants. On a per-player failure the worker continues other players then fails the invocation; Lambda retries and subsequent scheduled invocations re-query due items. No periodic table scan runs.

Times are deterministically randomized per player and UTC day. Default days have 2 or 3 slots, with expected mean 2.5; the execution-day counter ensures no more than 3 actual settlements per UTC day. If the service is delayed, it settles at most one overdue slot and plans from the current time rather than replaying a backlog. After re-enabling, at most one overdue attack is processed before scheduling from the current time. Delays or downtime therefore reduce the observed average. Errors and Lambda timeouts require CloudWatch monitoring; a poison record remains due for later retries. Receipts remain in the existing table; the API returns at most 40 latest records. Retention and scale should be reviewed before broad production activation.

Existing players need a **one-time**, resumable backfill; it uses a paginated table scan only when explicitly invoked and conditional puts never overwrite an existing schedule. New players are registered atomically at creation. Rerun the backfill after a partial failure to repair missing schedules. Its default mode is read-only. It creates no table and does not reset collection, bots, wallet or progress.

## Deployment order — only after approval

1. Build and release a compatible Unity client first. Old clients reject the four new bot IDs when a ten-bot list is returned. Verify RAID targets, incoming history and shield refresh on device before advancing.
2. Review a CloudFormation change set and current table/S3 policy. Deploy the backend, GSI, Lambda, IAM and EventBridge resources with the existing `python3 scripts/deploy.py --environment dev --profile yalla-dev --region ap-south-1`. This script uploads artifacts and changes AWS. Wait until the GSI and stack are active. The worker remains disabled because its default is false.
3. Publish `config/dev/bots.json` privately to `s3://yalla-result-pools-533266967583/game-config/dev/v1/bots.json` using `aws s3api put-object --bucket yalla-result-pools-533266967583 --key game-config/dev/v1/bots.json --body config/dev/bots.json --content-type application/json --server-side-encryption AES256 --if-none-match '*' --profile yalla-dev --region ap-south-1`. This is an AWS write and requires approval. For later updates use the current ETag with `--if-match`; do not overwrite an unknown version. Never use a public ACL.
4. Register a test player first, as below. After test approval, run the backfill dry-run and then `--apply` for all existing profiles. Monitor failures and rerun after interruptions.

## One-player test — only after approval

Set `PLAYER_TABLE` to the stack output and `AWS_PROFILE=yalla-dev`, `AWS_REGION=ap-south-1`. First run `node --import tsx scripts/backfill-incoming-raid.ts --player-id <test-player-id>` (read only), then repeat with `--apply` after approval. If already registered, it is not overwritten. Prepare a copy of `bots.json` with `incomingRaid.enabled=true` and `allowedPlayerIds` containing **only** that player ID. Validate it using `node --input-type=module -e "import {botsSchema} from './dist/bots-config.js'; import {readFileSync} from 'node:fs'; botsSchema.parse(JSON.parse(readFileSync(process.argv[1],'utf8')))" <path>`, then conditionally upload using the current ETag. Wait for the scheduled `dueAt` and five-minute worker cadence. Inspect that player's `INCOMING#SCHEDULE`, `INCOMING#RECEIPT#` and `COLLECTION` before and after; shield drops once if nonzero, otherwise remains zero. Retry the worker and verify the same sequence has no second receipt or debit. Reconnect Unity and inspect HISTORY and the Shield HUD. Reset `enabled` to false after testing with a conditional upload.

## All-player activation — only after approval

Complete and verify the one-time backfill first. In the approved private config set `enabled=true` and `allowedPlayerIds=[]`, validate and conditionally upload. Observe worker errors, throttling, due-time lag, DynamoDB and Lambda usage. This allows all registered players and changes live player shields; never do it without explicit approval. To pause, set `enabled=false`; warm processes refresh within 60 seconds when S3 is reachable. During an S3 outage warm instances can retain the last enabled config until a successful refresh, so disabling the EventBridge rule is the operational hard stop.
